# ブラックホールのそばで、光はどう曲がる？

文化祭のポスターから来てくださった皆さんへ。  
ブラックホールの向こうに模様のついた板があったら、私たちにはどう見えるでしょうか？

この研究では、ブラックホールの近くを通る**光の道筋をコンピューターで計算**し、背景の模様がゆがんで見える様子を調べています。光が吸い込まれる場合、曲がって背景に届く場合、背景を外れる場合を、3Dの経路と観測画像で見比べられます。

## ここが見どころ

- **光の進み方を比べる**：「ねらいのずれ」を変えると、光の行き先はどう変わる？
- **画像の1点から道筋をたどる**：生成した像をクリックすると、その画素に対応する光線を3Dで表示。
- **重力の有無を比べる**：同じ背景がどのように変形するかを並べて確認。

![光線の3D経路・生成された像・重力がない場合の比較プレビュー](validation/gui_preview.png)

上は、アプリ内の図を保存した**旧設定（背景の半幅12M）でのプレビュー**です。左が光線の経路、右上が観測像、右下が重力なしの比較像です。現在のコードでは背景の半幅が24Mなので、像や光線の到達判定はこの画像と異なる場合があります。実際の天体写真ではなく、計算で作った画像です。

## 見る・体験する

**スマートフォンでは、このページと画像を閲覧できます。現在のアプリはTkinterを使ったパソコン用で、スマートフォンやブラウザー上から直接起動することはできません。** 自分で操作するには、Pythonと画面表示が使えるWindows・Mac・Linuxのパソコンが必要です。

ここはGitHubという、プログラムを公開する場所です。ページ上部の「Code」にあるファイルは、計算の仕組みや画面を作るための「設計図」にあたります。読むだけならインストールは不要です。動かす場合は、次の手順で一式をダウンロードしてください。

## パソコンで起動する

1. Python 3を用意します。保存済みの検証記録はPython 3.13.12／Windows 11でのものです。Mac・Linuxを含む全環境での動作確認を意味するものではありません。
2. このページ上部の **Code → Download ZIP** でダウンロードし、ZIPを展開します。
3. 展開したフォルダー（`requirements.txt` と `ray_tracing_3d.py` がある場所）を、WindowsならPowerShell、Mac・Linuxならターミナルで開きます。
4. 次を順に実行します。

```sh
python -m pip install -r requirements.txt
python ray_tracing_3d.py
```

Mac・Linuxなどでコマンド名が `python3` の場合は、両方の `python` を `python3` に置き換えてください。Windowsで `py` を使う場合も同様です。同じPython環境にライブラリを入れて起動してください。

必要なライブラリはNumPy、Matplotlib、Pillowです。通常の起動にSciPyは不要です。Tkinterはpipで入れるライブラリではなく、Python側のTcl/Tk環境を使います。`python -m tkinter` で確認用のウィンドウが開けば準備できています。開かない場合は、Windows・MacではTcl/Tkを含むPython環境、Linuxでは利用中の配布元のTkinterパッケージ（例：`python3-tk`）を用意してください。

日本語が四角で表示される場合は、日本語フォントも確認してください。アプリはYu Gothic、Meiryo、Noto Sans CJK JP、IPAexGothicを順に探します。

## まずはこの順で操作

1. **「3本を比較」**を押すと、ねらいのずれ `b/M = 4.5, 6, 10` の経路を表示します。左の3D図はドラッグで回転できます。
2. **「光線のねらいのずれ b/M」**と**「軌道の向き ψ」**を変え、**「光線を発射」**を押して比べます。「停止 / 再開」でアニメーションを切り替え、「視点を戻す」で視点を戻せます。
3. 背景を「色つき格子」または「星空」から選び、最初は解像度128で**「像を生成」**を押します。画角・背景の回転を変えたら、もう一度生成してください。
4. 生成された右上の像をクリックすると、その画素の光線を左に表示します。**「JPGで保存」**で生成像を保存できます（画面全体の保存ではありません）。

背景の回転は、固定した正方形の中の模様の回転です。背景板そのものの向きや光線の経路は変わりません。「星空」も有限の板に描いた模様です。

| 生成画像の色 | 意味 |
| --- | --- |
| 背景の模様 | 追跡した光線が背景スクリーンに到達 |
| 黒 | ブラックホールに捕獲 |
| 濃灰 | 計算の外側境界まで追跡したが、スクリーンに未到達 |
| マゼンタ | 計算回数の上限に達し、未判定 |
| 赤 | 数値エラー |

3Dの線は別の配色で、水色が到達、橙が捕獲、灰が未到達です。黒と濃灰は意味が違います。有限の背景を使うため、暗い部分すべてがブラックホールの影を表すわけではありません。

## どんな原理で計算するの？

重力があると、時空の形が変わり、光の道筋も曲がります。このモデルでは、回転せず電荷を持たないブラックホールを表す**Schwarzschild（シュワルツシルト）時空**を使います。その中で光が進む道筋を「光の測地線」と呼びます。

- **事象の地平面：半径2M**。ここまで到達した光線を「捕獲」とします。
- **光子球：半径3M**。光が円軌道を取り得る場所ですが、その軌道は不安定です。
- **臨界衝突パラメータ：b = 3√3M ≈ 5.196M**。遠方から入射する光の捕獲と散乱を分ける理論上の境目です。`b` はねらいのずれを表す量で、最接近距離そのものではありません。有限のスクリーンへの到達条件は、さらに背景の大きさや軌道の向きにも依存します。
- **RK4（4次のルンゲ＝クッタ法）**。光の運動を表す微分方程式を、小さな区間に分けて数値的に解きます。

ここでは `G=c=1` の単位系を使い、長さをブラックホールの質量に対応する尺度 `M`（通常の単位では `GM/c²`）で表します。コードではさらに `M=1` としています。

像を作るときは、観測者から各画素の方向へ光線を**逆向きにたどり**、背景のどこに行き着くかを調べて、その場所の色を読み取ります。3D図は座標で表した説明図で、アニメーションの速さは光の実際の移動時間を表していません。降着円盤の発光やブラックホールの回転を再現するモデルではありません。

## 計算の信頼性について

刻み幅を小さくしたときに結果が落ち着くか、別の高精度な計算法と一致するか、画像と3Dの経路が対応するかを確認するための検証コードを公開しています。

**ただし、現行コードと保存済み検証には設定の違いがあります。** 現在の `ray_engine.py` は背景の半幅24Mです。一方、保存済みの検証値・画像、およびテストや独立比較の一部は半幅12Mを前提としています。現行コードで自動テストを再実行した結果は**25件中19件成功・6件失敗**でした。旧設定での「25件成功」や誤差表を、現行設定での検証完了を示す数値として読むことはできません。

変更はREADMEに限定し、エンジン・テスト・保存画像はそのままにしています。精密な研究利用では、まずスクリーン条件をそろえて再検証する必要があります。

## 物理条件と停止判定

- Schwarzschild 時空、G=c=M=E=1。観測者は (30,0,0) の静止観測者。
- 放射面は **x=-19、|y|≤24、|z|≤24 の有限正方形**。外側境界は **r=120**。
- 軌道がスクリーンと交差すると交点で停止して「スクリーン到達」。
- スクリーンより先に r=2 に達すると「捕獲」。
- スクリーンを外れた光線も追跡を続け、外側境界で「スクリーン未到達」。
- スクリーンの外で x=-19 を横切るだけでは停止しません。その後の有効な交差も検出します。
- 計算回数の上限は「未判定」、非有限値などの計算異常は「数値エラー」とし、未到達と区別します。

元の微分方程式と RK4 関数はそのままです。

```text
dr/dλ   = v
dv/dλ   = b²/r³ (1 - 3/r)
dφ/dλ   = b/r²
r(0)    = r0
v(0)    = -sqrt(1 - b²/r0² (1 - 2/r0))
φ(0)    = 0
```

カメラの局所角度 α と b の関係も `b=r0 sin(α)/sqrt(1-2/r0)` を保持しました。
刻み幅は従来の `h=min(0.7,0.006*r)`、収束確認時はこれに `scale` を掛けます。
光線をスクリーンへ向け直す処理や、脱出後に直線を付け足す処理はありません。

各 RK4 ステップの状態を次の座標に変換します。

```text
x = r cosφ
y = r sinφ cosψ
z = r sinφ sinψ
```

隣接する点 P0、P1 の線分について、平面との交差率を
`t=(-19-P0.x)/(P1.x-P0.x)` で求めます。`0≤t≤1` かつ交点の y,z がスクリーン内の場合だけ有効です。
球面境界は **同じ線分** と球の交差から t を求め、スクリーン・地平面・外側境界のうち
最小の t を選びます。これにより、同一ステップ内でスクリーンと外側境界を横切っても
到達順を保ちます。同時の場合は地平面、スクリーン、外側境界の順で優先します。
スクリーン終点は x=-19 に正確に置き、地平面と外側境界も球面上に補間します。

## 画像と GUI

従来の Tkinter 操作、3D回転、アニメーション、画像クリック、JPG保存を保持しています。
「3本を比較」は b=4.5,6,10 を使います。分類は現在のスクリーン条件で計算され、旧設定の3分類になるとは限りません。

3Dの平面には **放射源の模様** を表示します。観測像を平面に貼り戻すことはしません。
生成像と「重力がない場合」の比較像は、その同じ平面の同じ座標の色を読み取ります。
背景の回転は固定した正方形の中の模様の回転です。スクリーンや測地線の向きは変えません。
表示中の像と3D背景は、最後に画像を生成した時点の背景設定を共有します。

| 画像の色 | 意味 |
| --- | --- |
| スクリーンの模様 | 到達した交点の色 |
| 黒 RGB(0,0,0) | 地平面に捕獲 |
| 濃灰 RGB(28,36,48) | 外側境界まで追跡したがスクリーン未到達 |
| マゼンタ RGB(255,0,180) | 回数上限で未判定 |
| 赤 RGB(255,64,64) | 数値エラー |

未到達の光線に背景色を割り当てたり、捕獲と同じ黒にしたりしません。
重力なしの比較像もスクリーン外を濃灰にします。
保存する JPG も同じ配色です。JPEG 圧縮によって個々の RGB 値は変わる場合があります。

画像クリック時は、クリックした画素の中心に対応する b,ψ を計算します。
3Dと画像は同じ追跡エンジンと停止判定を使います。
アニメーションの間引きでも最終点を必ず表示するため、到達線がスクリーン手前で途切れません。
未到達線の r=120 の終点は初期表示範囲外になることがありますが、経路データには含まれます。
3D表示は Schwarzschild 座標による説明図です。描画順は従来と同じく固定し、厳密な遮蔽計算は行いません。
アニメーションの速度は座標時間を表していません。

正方形スクリーンは軸対称ではなく、到達判定は軌道の向きにも依存します。
画像生成では **b と max(|cosψ|,|sinψ|) がともに一致する光線** だけ計算を共有します。
これは正方形の反転・90°回転対称性の利用です。異なる b の間を補間しません。
光線の分類は模様の色には依存しないので、背景を回転しても分類は同じです。

## 検証結果

以下は**半幅12Mで保存された過去の検証記録**です。現行の半幅24Mに対する精度保証ではありません。過去の記録では25件の自動テストが通過しました。`test_screen.py` は、同一ステップ内の到達順序、スクリーンの端、範囲外通過後の再交差、
向きによる分類差、3Dとバッチの終点一致、臨界付近の分類、未判定・数値エラーの色、
クリック画素と個別追跡、平面の比較像、回転した3D格子の位置を検証します。

```powershell
python -m unittest -v test_screen
```

独立した SciPy DOP853 積分（rtol=1e-12、atol=1e-13、max_step=0.2）と、
臨界値 sqrt(27) の近くを含む22条件で比較しました。
以下は全条件で分類が一致した比較結果です。

| 刻み倍率 scale | 最大スクリーン交点差 [M] | 最大 RK4 保存量誤差 |
| --- | ---: | ---: |
| 1 | 1.54×10⁻⁴ | 9.00×10⁻⁹ |
| 1/2 | 9.63×10⁻⁶ | 5.52×10⁻¹⁰ |
| 1/4 | 6.00×10⁻⁷ | 3.42×10⁻¹¹ |

終点を線分補間するため、終点座標・速度の精度は RK4 単独の4次精度と異なります。
保存量 `Q=v²+b²/r²*(1-2/r)` の誤差は、RK4の格子点と補間後の状態を別々に記録しています。
22条件の補間後の最大 |Q-1| は scale=1 で約1.23×10⁻⁴、scale=1/4 で約3.29×10⁻⁶でした。
この値を積分器そのものの保存量誤差と混同しないようにしています。

臨界に非常に近い光線は誤差に敏感です。
今回の最大の全終点差は、b=sqrt(27)+2×10⁻⁷ の未到達線の r=120 終点で、
scale=1 の約1.69×10⁻² M から scale=1/4 の約6.89×10⁻⁵ M に減りました。
全ての b に対する誤差上限や、スクリーン端のすぐ近くでの分類一致を保証する値ではありません。
研究用の境界判定や高次像には `scale=0.5` または `0.25` で収束を確認してください。

画像生成（画角45°、色つき格子）の実測値は次のとおりです。
時間はこの端末での参考値で、CPU負荷によって変動します。

| 解像度 | 独立に積分する組 | 到達 | 捕獲 | 未到達 | 所要時間 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 128×128 | 2,080 | 11,372 | 2,156 | 2,856 | 約1.9秒 |
| 256×256 | 8,256 | 45,456 | 8,628 | 11,452 | 約3.8秒 |
| 512×512 | 32,896 | 181,780 | 34,568 | 45,796 | 約10.9秒 |

いずれも未判定・数値エラーは0でした。
128×128では、scale=1 と scale=1/2 の全RGB画素値が一致しました。
元の `derivatives` と `rk4` は構文木比較で同一、従来の球面モードでの分類と
補間前の保存量誤差も元のエンジンと一致しました。

Tkinterの実ウィジェットを非表示ウィンドウで生成し、比較発射、停止切替、視点リセット、
別スレッドでの画像生成、画素クリック、アニメーション終点、JPG保存を自動検証しました。
手動のドラッグ操作や OS の保存ダイアログの操作は自動検証には含めていません。
`validation/gui_preview.png` は実際のアプリの Figure から保存したプレビューです。

### 再実行と現在の注意点

`test_screen.py` の一部は端の座標や期待する分類を12Mで固定しています。今回の現行コードでの再実行では、端の判定、範囲外通過、回転格子、比較像、経路終点、向きによる分類差の6テストが失敗しました。また、`validate_screen.py` の独立DOP853比較は半幅12Mを直接指定し、GUI検証も旧設定での3分類を期待します。したがって、次のコマンドだけで現行24Mの検証が完了するとは限りません。

```sh
python -m unittest -v test_screen
python -m pip install scipy
python validate_screen.py --scipy --gui
```

SciPyは独立比較だけに必要です。`python validate_screen.py --gui` ならSciPy比較を省略できますが、GUIの旧設定への依存は残ります。GUI検証には画面表示できる環境が必要です。

検証スクリプトは `validation/` に結果や画像を書き出し、既存の記録を上書きします。残したい記録は事前に別の場所へ保存してください。途中でassertionが失敗した場合は、検証完了とは扱わないでください。

`--original-dir PATH` は旧コードの `ray_engine.py` との比較用です。旧版を別途用意した場合だけ指定します。現在のリポジトリ自体を旧版の代わりに指定しないでください。

保存記録：[詳細な検証結果](validation/validation.json)、[当時のソースハッシュ](validation/source_hashes.json)。ルート直下の `validation.json` は別ファイルです。ソースハッシュは保存時点の記録で、現在のコードすべての検証済み証明ではありません。

## コードから使う場合

`trace_batch` の戻り値は従来どおり `(states, status, error)` の3要素です。
状態番号は 0=未判定、1=捕獲、2=スクリーン到達、3=未到達、4=数値エラーです。
`psi` はスカラーまたは b と同じ長さの配列を受け付けます。
`sky` 引数は外側計算境界の半径を指定する従来名です。
エンジン単体の既定 r0=40,sky=400 は互換性のため保持し、GUIと画像は共通定数30,120を明示します。

```python
from ray_engine import trace_batch
s, status, error = trace_batch([7., 7.], r0=30., sky=120., psi=[0., 0.7853981633974483])
# 現行の半幅24Mでは status: [2, 2]（両方スクリーン到達）

from imaging import render_image, trajectory
image, reference, meta = render_image(256, scale=0.5)
path, label = trajectory(10., psi=0.3, scale=0.5)
```

球面背景用の `build_lut()` は明示的な `screen_x=None` モードを使い、従来形式を保持します。
この旧モードに限り status=2 は球面到達です。有限スクリーンの画像生成には使いません。
`background(points,...)` の引数は、従来の単位球面方向からスクリーン上の実座標に変わります。
新規コードでは `screen_background(y,z,...)` を使ってください。

主なファイルは、画面を作る [ray_tracing_3d.py](ray_tracing_3d.py)、測地線を計算する [ray_engine.py](ray_engine.py)、画像を作る [imaging.py](imaging.py)、依存関係を示す [requirements.txt](requirements.txt)、自動テスト [test_screen.py](test_screen.py)、数値・GUI検証 [validate_screen.py](validate_screen.py) です。GUIは `geodesic.py` をインポートしません。

なお、現行GUIの説明ラベルには半幅12Mという旧表記が残り、3D図の初期表示範囲も半幅24Mのスクリーン全体を収めません。実際の計算条件は `ray_engine.py` の定数で確認してください。
